# skill-reviewer（スキル文書をレビューする役）

## 前提となる言葉

この文書を読むのに必要な言葉を先に説明する。

- **スキル** — このリポジトリが配っている「エージェント（AI に作業させる仕組み）への手順書」のこと。1 つのスキルは `skills/<名前>/SKILL.md` という手順書本体を持ち、必要に応じて補足資料や小さなスクリプトを従える。
- **cycle** — 実装計画を受け取り、修正・レビュー・検証を自動で回して実装まで持っていくスキル。この文書に出てくる「自動で止まる／続く」はすべて cycle の中の話である。
- **plan-reviewer** — 実装計画そのものをレビューする別のスキル。コードの正しさや安全性を見る力はこちらが持っている。
- **skill-reviewer** — 本文書が定めるスキル。**スキルの手順書そのもの**をレビューする。

## このスキルの位置づけ

skill-reviewer は、スキルを構成する文書とファイルだけを見るレビュー役である。具体的な対象は次のとおり。

- `skills/<名前>/SKILL.md` — スキルの手順書本体
- `skills/<名前>/references/` 配下 — 手順書が参照する補足資料
- `skills/<名前>/fixtures.json` — そのスキルの振る舞いを再現テストするための入力と合格条件をまとめたファイル（後述の「fixture」）
- `skills/<名前>/scripts/` 配下 — スキルに付属する小さなプログラム
- `skills/shared/references/` 配下 — 複数のスキルが共通で参照する取り決め文書
- `commands/` 配下の `.md` ファイル — スキルを呼び出すための入口

ただし `scripts/` 配下の扱いには例外があり、次の節で述べる。

**このスキルは「通す／通さない」を決めるゲートではなく、診断器である。** 機械的に合否を決める役目は、すでにある 2 つの仕組みが担っている。1 つは `sh scripts/run_checks.sh`（このリポジトリの検証をまとめて走らせるコマンド）、もう 1 つは回帰台帳（後述）である。skill-reviewer はそこへ新しい強制を一切足さない。見つけたことを構造化して報告するだけで、最終的に止めるかどうかを決めるのは cycle と人間である。

## 担当範囲の境界

### スクリプトは cycle の中では plan-reviewer が見る

`skills/<名前>/scripts/` 配下のプログラムは、skill-reviewer を直接呼んだときには診断対象に含まれる（スクリプトの堅さや、責務の置き場所が妥当かという観点で見る）。しかし cycle の中の振り分けでは、**scripts はこのスキルではなく plan-reviewer に回す**。この裁定は課題管理の #200 番（cycle 内でどちらのレビュアーが scripts を担当するかを決めた検討）で確定した。

理由は 2 つある。

1 つ目。skill-reviewer が生まれた背景は、#190 番の課題で起きた事故である。そこでは自然言語で書かれたスキル文書に対して「指摘の取りこぼしを減らす方向へひたすら最適化されたレビュー」をかけた結果、指摘と書き直しの往復が 22 周続いて終わらなくなった。この病理は散文特有のもので、プログラムには当てはまらない。

2 つ目。skill-reviewer が「止める」と言える指摘には後述の厳しい条件（すでに存在する機械的な証拠を指せること）がかかっている。プログラムの新しい不具合 — 境界値の取り違え、外部入力の混入、処理順序の誤り — は、その場ではまだ証拠が存在しないので、この条件の下では「止める」に届かず注意止まりになってしまう。コードの正しさと安全性で実際に止める力は plan-reviewer に置くのが妥当である。

### 振り分けが効くのは cycle の 1 局面だけ

上のレビュアー振り分けは、cycle の中の実装レビュー局面（Phase 3）に限った話である。cycle の最後にある最終ゲート（Phase 4）は、変更されたファイルの種類を見ない。すべてのファイルを、全体を通しで見るレビューと外部レビューにかける。

最終ゲートの通しレビューは、#190 で事故を起こした「観点ごとに取りこぼしを潰していくレビュー」とは別物である。加えて最終ゲートには指摘 → 修正 → 再レビューの自動往復がないので、指摘が散文を呼び、散文がまた指摘を呼ぶという無限往復は構造的に始まらない。

## 出力は 2 本の系統に分かれる

skill-reviewer の出力は 2 つの系統に分かれ、**cycle が制御の判断（止める・直す）に使ってよいのは片方だけ**である。この分離は口約束ではなく、レビュアーが出力を作る時点で形式検査（決められた形になっているかを機械的に確かめる検査）によって強制される。

一方、受け取った側がその分離を守るかどうかは、まだ機械では強制していない。受け取り側は本文書が定める分岐の表に従う、という取り決めで運用する（受け取り側の機械強制と、このスキル自身の再現テストの登録は、別の課題として残っている）。

### 制御に使える系統

こちらの系統（出力では `control_candidates` と呼ぶ）に入るのは、cycle が読んで動きを変えてよい指摘である。

- **BLOCK（止める）と言えるのは、すでに存在する機械的な証拠を指せる指摘だけ。** 具体的には、実際に落ちているテスト、リポジトリ整合性検査（`scripts/validate_repo.py`）の違反、そして文書の本文だけで矛盾が証明できる取り決めの食い違い、の 3 種である。「たぶん危ない」は BLOCK にできない。
- BLOCK には**その資格を満たす理由**（出力上は `qualification_reason`）を必ず添える。理由のない BLOCK は形式検査で拒否される。この必須化は BLOCK だけにかかり、注意（WARN）には求めない。
- **WARN（注意）は記録して先へ進む。** 自動で直されるのは、その指摘に「自動修正してよい」という印（出力上は `fix_action: AUTO_FIX`）が明示されているものだけである。
- 止めるか直すかの最終判断を持っているのは cycle であって、レビュアーの判定は命令ではない。

### 記録だけの系統

もう一方の系統（出力では `diagnostics` と呼ぶ）には、注意（WARN）・改善余地（OPPORTUNITY）・参考情報（INFO）が入る。この系統は cycle の進行に一切影響しない。自動修正にも、再レビューにも、人間のいない自動実行を止める判断にも使われない。表示と記録だけである。

## 指摘の重さは 4 段階

外から見える段階は、重い順に BLOCK（止める）／ WARN（注意）／ OPPORTUNITY（改善余地）／ INFO（参考情報）の 4 つである。

指摘の重さの語彙は複数スキルで共有しており、正本は `skills/shared/references/severity-and-verdicts.md` にある。そこへ足すのは、OPPORTUNITY の 1 行と、skill-reviewer 固有の追加規則（BLOCK には機械的な証拠が要る）を書いた短い節だけに留める。skill-reviewer が内部で使っている「影響の大きさ」と「証拠の強さ」の 2 軸による細かい分類は、共有の語彙には持ち込まず、このスキルの内部規則のままにする。共有語彙を膨らませると、それを読む他のスキルすべてに負担が乗るためである。

## 「実際に動かした証拠」の扱い

### 重い実測は自分では走らせない

スキルの品質を測る方法には、AI に実際にスキルを走らせて結果を採点する重い手段がいくつかある。このリポジトリで言えば、再現テストの実走（skill-regression スキル）、スキルが正しく起動するかの動的評価（trigger-eval スキル）、指示文の質を反復計測する仕組み（empirical-prompt-tuning スキル）である。

**skill-reviewer はこれらを自分では回さない。** 自走してよいのは、結果が毎回同じで費用も安い検証だけ — つまり静的な検査と、付属スクリプトの単体テストである。

### 台帳の記録を 5 つの状態に読み替える

では実走の証拠はどこから得るのか。すでに記録されているものを読む。中心になるのが**回帰台帳**（`skills/skill-regression/ledger.json`）で、これは「どのスキルについて、いつ、どの入力で再現テストを走らせ、どういう結果だったか」を残す台帳である。ここで言う **fixture**（再現テスト用の一式）は、スキルに与える状況と、満たすべき条件の一覧をまとめたものを指す。

skill-reviewer は台帳の記録を次の 5 状態に読み替えて報告する。

| 状態 | 意味 |
|---|---|
| current_pass | 最新の内容で実際に走らせて合格している |
| accepted_without_run | 実際には走らせず、人が承認しただけ |
| stale | 走らせた記録はあるが、その後の変更で古くなっている |
| uncovered | 再現テスト一式が用意されていない、または台帳にそのスキルの記録がない |
| invalid | 記録が壊れている・整合しない |

**accepted_without_run を「実走の証拠あり」として表示してはならない。** これがこの節の要である。

台帳には、実際には走らせていないが機械的な確認を経た承認が 2 種類ある。1 つは `accepted-addition`（ファイル内容の指紋の突き合わせで「追加しかしていない」と機械確認したもの）、もう 1 つは `accepted-prose`（文書の構造の指紋を突き合わせて「既存の文書の地の文を言い換えただけ」と機械確認したもの）である。この 2 つも accepted_without_run として扱う。機械確認は**承認の安全度**を上げる話であって、走らせたことにはならない。だから 6 つ目の状態は作らない。

### 証拠がないことは減点ではない

実走の証拠が欠けている、あるいは古くなっているという事実は、**推奨止まりにして合否には絶対に入れない**。証拠なしは「指摘」ではなく、どこまで言えるかという網羅状況として申告する — 証拠に裏打ちされていない状態を `unsupported`、そもそも測っていない状態を `uncovered` と呼ぶ（出力にはこの 2 つの識別子をそのまま使う）。そして裏打ちのない領域について「問題なし」とは主張しない。

推奨を出すときは、その実測がどれだけの範囲に効くかと、おおよその費用を添える。実測にいつ支払うかを決めるのは人間である。

## OPPORTUNITY（改善余地）の扱い

OPPORTUNITY は記録だけの系統の専属である。注意（WARN）へ自動で格上げすることは禁止する。課題として登録するのは人間の明示的な操作でのみ行う。

再現テストの候補として拾い上げる（fixture 化する）のは、次の 3 つが揃ったときに限る。

1. 合格・不合格を外から観測できる条件がある
2. 再現できる重要な場面がある
3. 将来の回帰検出の資産として値打ちがある

材料が揃わなければ参考情報（INFO）に留める。

## 出力の先頭に「これは証拠ではない」と書く

skill-reviewer のすべての出力の先頭に、次の 3 つを固定で載せる。

- 保証上の役割は診断のみ（`assurance_role: diagnostic_only`）
- 品質ゲートの証拠ではない（`quality_gate_evidence: false`）
- 重い実測は 1 つも走らせていない（`dynamic_sensors_executed: []`）

ここで**品質ゲートの証拠**とは、「この変更は出してよい」と機械的に判定するために使ってよい記録のことである。skill-reviewer の出力をそれと取り違える経路を、構造的に潰しておくのがこの宣言の目的である。

## 判断表を 2 層にする理由

skill-reviewer が持つ判断表は 2 層でできている。

1. **変更の種類から引く層** — 何が変わったかに応じて、どの証拠を参照し、どの安い静的検査を自分で走らせるかを決める。
2. **主張の種類から引く層** — 得られた材料に対して、何を言ってよくて何を言ってはいけないかを決める。

2 層に分ける狙いは、**重い実測を回すかどうかをレビュアーの裁量にしない**ことである。この形なら、レビューにかかる費用が変更の種類から前もって読める。
