# 仕様反映の経路非依存化（どの経路で作っても仕様書への反映が残る仕組み）

## 前提となる言葉

- **仕様書（docs/spec/）** — 「なにを作るか」を人間が承認した正本のドキュメント群。
- **幹（trunk）** — このリポジトリが定める、なにかを作るときの正式な流れ。「発話または Issue →
  brainstorm（壁打ち）→ plan（実装計画）→ 実装 → レビュー → 文書への書き戻し → PR（プルリクエスト、
  変更の取り込み依頼）」。
- **brainstorm / wrap** — 壁打ちの対話で要件を詰める、幹の入口フェーズ。wrap はその成果をメモに
  まとめる締めの手順で、合意が収束したときは仕様書ドラフトを作り、人間の承認を経て docs/spec に書く。
- **plan / plan-create** — 実装計画と、それを作る手順。brainstorm 経由・issue 経由・手動のどの経路を
  とっても、計画はこの手順で生まれる。
- **issue** — 作業中に見つかった、いまの作業範囲の外にある問題の記録。issue から brainstorm を通らず
  直接 plan を作る経路が用意されている。
- **doc-check** — 実装のあとに、ドキュメントとコードの食い違いを検査して書き戻す仕組み。幹の
  「文書への書き戻し」の駅にあたる。
- **push ゲート** — エージェントの git 操作（変更の公開）を実行直前に検査する仕組み。push には
  文書整合チェックを実施した記録が要る。詳細は [workflow-enforcement.md](workflow-enforcement.md)。

## 解決する問題

仕様書を書く責務が brainstorm の wrap だけに置かれている。そのため brainstorm を通らない経路 —
issue から直接 plan を作る、手動で plan を書く — では、仕様変更を伴う実装でも仕様書を書く工程が
経路上にそもそも存在しない。

入口で brainstorm へ誘導する案内は常駐しているが、会話のような形の依頼では誘導の判定自体が走らない
ことが実測されており、入口の発火は確率的にしかならない。入口に責務を置く限り、経路の差でこの穴は
塞がらない。

## 方針 — 入口で保証せず、合流点で保証する

どの経路でも必ず通る地点（合流点）に、「仕様反映の要否を必ず 1 回問う」仕掛けを置く。

1. **plan の Spec Impact 欄（必須）** — すべての plan は「仕様への影響: あり（仕様書パスまたは
   ドラフト参照を添える）/ なし（なしと明示宣言する）」の記録を持つ。記録先は plan ヘッダーの
   `**Spec:**` 欄で、値の語彙は 3 形のみ: `{docs/spec のパス}`（影響あり・承認済み仕様書が存在
   または本作業で更新）/ `draft {パス}`（影響あり・未承認ドラフト）/ `none — {一行の理由}`
   （影響なしと判断、理由必須）。要否の判断そのものはエージェントと人間が行い、機械的に検査
   できるのは「行が存在し、3 形のいずれかに一致する」ことである。旧形式（`**Spec:**` 行のない
   既存 plan）は修正不要で、必須化は新規作成される plan に適用する。
2. **doc-check の宣言照合** — 実装後の検査で、plan の Spec Impact 宣言と実際の変更内容を
   突き合わせる。「なし」と宣言したのに仕様的な挙動変更が差分にあれば指摘する。既存の検査観点の
   拡張であり、新しい仕組みは足さない。
3. **push ゲートは変えない** — 文書整合の実施記録の要求は既にあり、上の 2 つが機能すれば検出の網が
   細かくなるだけで、ゲート自体の変更は不要。

## 変わらないこと — wrap は「最も手厚い入口」として残る

brainstorm wrap の仕様書生成は廃止しない。対話で収束した合意を人間承認付きで仕様化する品質は、
他の経路では代替できない。合流点の保証は、wrap を通らなかった場合のセーフティネットであり、
置き換えではない。

## 未決事項

- issue から plan を作る経路に軽量の brainstorm（十分に練られた issue が 1 ラウンドで収束する形）を
  挟むかは、合流点設計の効果を見てから判断する。
- 機械検査（3 形への一致）をスクリプト（validator）にするかは、doc-check の宣言照合の効果を
  観測してから判断する（値の語彙そのものは上記の 3 形で確定済み）。
- 検出精度の検証方法は、実装完了後にまとめて設計する（検証を省くのではなく、支払い方を後で決める）。

## この仕様が変わるとき

合流点の位置（plan・doc-check）や Spec Impact 欄の意味を変える変更は、brainstorm の合意を経て
本ファイルを更新してから行う。
