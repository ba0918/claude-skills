# semantic triage（変更の影響を LLM が精査する判定器）

## 前提となる言葉

この文書を読むのに必要な言葉を先に説明する。

- **スキル** — このリポジトリが配っている「エージェント（AI に作業させる仕組み）への手順書」。1 つのスキルは `skills/<名前>/SKILL.md` という手順書本体を持つ。
- **共有契約** — `skills/shared/references/` 配下にある、複数のスキルが共通で参照する取り決め文書。1 つ直すと参照している全スキルの挙動が変わりうる。
- **fixture** — `skills/<名前>/fixtures.json`。そのスキルの振る舞いを再現テストするための「場面（シナリオ）と合格条件（要件）」を集めたファイル。
- **実走** — fixture のシナリオを実際にエージェントに実行させ、要件を満たすか確かめること。1 スキル分で数十万トークン級の費用がかかる。
- **回帰台帳（ledger）** — `skills/skill-regression/ledger.json`。「このスキルはこの内容の時点で検証済み」という記録。関係するファイルが変わると記録が古い（stale）と判定され、CI が「再検証するか、不要と判断した記録を残すか」を要求する。**台帳が強制するのは『無視ではなく、記録された判断』だけ**であり、再走そのものを強制する仕組みはもともと存在しない。
- **accept** — 実走せずに「この変更は挙動に影響しない」と人間が判断して台帳を進める操作。判断であることが分かる形（`accepted-*` という値）で記録され、実走由来の `pass` とは区別される。
- **severity（変更の重さ分類）** — 台帳が変更を機械分類する 3 値。散文の言い回しだけが変わった `prose-change`、ファイルが増えただけの `contract-addition`、それ以外すべての `contract-change`。前 2 者は機械が「安全な形」と証明できるため安価に処理でき、`contract-change` だけが実走か人間の accept を要する重い帯として残る。

## 解決する問題

共有契約の編集は直近 14 日間で 63 コミット（1 日あたり約 4.5 件）発生している。現在の機構は「ファイルが変わったか」をハッシュ比較で検知するが、これは「挙動に影響があるか」の**過大近似**である — 重複した指示を 1 つ削っただけでも、影響を受ける*可能性のある*スキルすべてが再検証対象になる。影響の有無は自然言語の解釈の問題であり、機械のハッシュ比較では原理的に判定できない。その結果、実際には無害な変更に対して「高価な実走」か「人間の目視 accept」のどちらかを毎回払っており、費用対効果が釣り合っていない。

semantic triage はこの中間帯に入る判定器である。変更前後の差分（diff）を LLM が読み、対象スキルの要件と突き合わせて「影響なしと言い切れるか」を精査する。無害と精査できた変更は安価に台帳を進め、それ以外は今までどおり人間の判断に委ねる。

## 判定器の仕事

### 入力

1 回の判定は「1 つの diff × 1 つのスキル」を単位とする。判定器に渡すのは:

- 変更前後の差分（diff 本文）
- 対象スキルの各シナリオの**タイトルと要件テキスト**（fixtures.json の全文や、シナリオの状況設定文は渡さない — 判定に必要なのは「この差分が各要件の合否判定を変えうるか」だけであり、要件テキストなら数キロバイトに収まる）

### 出力は 3 値

判定は連続スコアではなく 3 値で返す。

| 判定値 | 意味 | その後の扱い |
|---|---|---|
| `unaffected` | この差分は当該シナリオの要件充足に影響しないと言い切れる | 台帳を `accepted-semantic`（後述）として進められる |
| `unclear` | 影響の有無を言い切れない | 人間への**推奨表示のみ**。判断は人間 |
| `affected` | 要件充足に影響しうる | 人間への**再走推奨の表示のみ**。強制しない |

判定はシナリオごとに返す（1 スキル 1 呼び出しで、シナリオ別の判定表を出力する）。これにより「影響ありのシナリオだけ部分再走する」という既存機構（`--partial --scenario`）にそのまま接続できる。

連続スコア + しきい値を採らない理由: LLM が返す数値スコアは分布が安定せず、しきい値の較正が見かけの精密さになる。3 値なら較正対象を「`unaffected` 判定の誤り率」1 点に絞れ、「迷ったら重い側へ倒す」というこのリポジトリの安全設計とも揃う。

### 出力に必ず添えるもの

- 判定の**根拠**（どの要件にどう影響する / しないか、1〜3 行）
- **判定に使ったモデルの識別子**（較正はモデルに固有であり、モデルを変えたら再較正が必要になるため）
- **判定対象の diff のハッシュ**（古い判定を別の変更に使い回す事故を機械的に防ぐため）

## 権限の境界（この仕様で最も重要な取り決め）

**判定器は、どの方向にも実行の権限を持たない。**

- `affected` と判定しても、再走を自動で開始することは**絶対にしない**。表示するのは推奨まで。再走するか、それでも accept するかは今までどおり人間が決める。
- `unaffected` と判定した場合に限り、台帳へ記録するという 1 点だけが機構に接続される。これも「記録」であって実行の制御ではない。
- 台帳のゲートの意味（変わったものは、記録された判断なしには緑に戻らない）は一切変えない。判定器は「判断を安く・速くする層」であって、新しい強制でも新しい抜け道でもない。

この境界の理由: 再走コストの高さが問題の根本であり、判定器に強制力を持たせると、判定器の誤りがそのまま高価な再走を量産する。また「可能性の情報」に実行権限を与えないという原則は、宣言（exercises）が「可能性ゼロの人間宣言」だから台帳判定に使ってよい、という既存設計との一貫性でもある — **情報の確度と、機構上の権限を一致させる**。

## 記録の形式 — accepted-semantic

`unaffected` 判定で台帳を進めた記録は、新しい分類 `accepted-semantic` として残す。既存の分類との関係:

| 記録値 | 誰が・何が判断したか | 確度の性質 |
|---|---|---|
| `pass` | 実走した | 実測 |
| `accepted-prose` / `accepted-addition` | 機械の決定的な形状証明 | 証明（決定的） |
| **`accepted-semantic`（新設）** | **較正済み LLM 判定器** | **確率的判断** |
| `accepted-without-run` | 人間の目視判断 | 目視 |

取り決め:

- `accepted-semantic` は **`pass` を名乗らない**。「pass = 実走で確かめた」はこの台帳の生命線であり、実走なしの判断が pass に化ける経路は過去のレビューで繰り返し塞いできた。
- 記録には 3 値判定・根拠・判定モデル識別子・diff ハッシュを必ず含める。形式を満たさない記録、および diff ハッシュが現在の差分と一致しない記録は、台帳側が拒否する。
- 台帳の集計表示（`--check`）では `accepted-semantic` を**独立のカウント**として出す。他の accepted と混ぜると「判定器に寄りかかりすぎている」という新しい危険信号が読めなくなるため。
- **意味論を正直に書く**: `accepted-semantic` が意味するのは「挙動が変わらないことの証明」ではなく、「**維持者の判断方針に較正された判定器が、影響なしと判断した**」である。実際に挙動が変わったかどうかは実走でしか分からない。別の理由で実施される実走（fixture の変更時など）が、蓄積した `accepted-semantic` の抜き打ち監査を自然に兼ねる。

## 組み込み位置

判定器が呼ばれるのは **severity 分類で `contract-change` になった変更だけ**である。`prose-change` と `contract-addition` は既存の決定的な機械証明で既に安価に処理できており、そこに確率的判断を重ねる理由がない。判定器は「機械が安全と言い切れず、現状では実走か目視 accept に落ちている中間帯」だけを引き受ける。

役割分担は次のとおり:

- **判定そのものは LLM が行う**（スキルの手順書に「contract-change の stale には semantic triage を回す」という手順として組み込む）。
- **スクリプト（ledger.py）は LLM を呼ばない**。スクリプトが保証するのは、記録の形式検査と diff ハッシュの束縛検査だけである。判断はことばの側に、保証はコードの側に置く、というこのリポジトリの責務配置に従う。

## 較正 — 判定器自身の誤り率を測ってから権限を与える

「影響は解釈次第で測れない」と言った当のものを LLM に判定させる以上、**判定器自身の当てにならなさ**を先に測る。危険なのは偽陰性（「影響なし」と言ったが実際は影響があった）の方向である。

### 較正コーパスは両面で作る

| 側 | 内容 | 測るもの |
|---|---|---|
| **must-flag 側**（20〜30 件） | 挙動が変わることに争いのない編集を意図的に作る: 要件の否定化、数値の変更、手順の順序入れ替え、重複していない指示の削除 | 偽陰性率。**ここで 1 件でも `unaffected` を返す間は、自動記録を解禁しない** |
| **must-pass 側**（20〜30 件） | 影響しないことに争いのない編集: 「Aを行う」→「Aを行ってください」のような言い回し変更、実際の変更履歴から拾った散文級の編集 | 偽陽性率。安全側の誤りだが、高いと節約効果が消える |
| **グレー帯** | 判断が分かれる編集（例: 重複する指示の削除。維持者の裁定は「影響なし」） | 維持者が 1 件ずつ裁定してラベル付けし、その裁定を判定器の基準文と例示に反映する。判定器が維持者の裁定を再現できるかを測る |

なお「言い回しを変えただけ」の編集は mutation（挙動を変える変異）ではない。較正コーパスの must-flag 側に紛れ込ませてはならない — 判定器を実際より悪く見せ、しきい値を無意味に厳しくする。

### 暫定の解禁ライン

must-flag 側の偽陰性 **0 件**を、自動記録解禁の暫定ラインとする。届かない間は advisor モード（後述）に留めて運用し、運用データが溜まった時点でラインの見直しを判断する。この「見直してよい」という条件付きであることも仕様の一部である — 基準の根拠が経験不足である以上、最初のラインを恒久ルールにしない。

### モデルとの束縛

較正はモデルに固有である。判定モデルを変更したら再較正するまで自動記録は無効に戻る（記録に判定モデル識別子を必須で残すのはこのため）。既定のモデル選定は「実測系の実行は標準的なモデルを既定とする」という既存の運用裁定に従う。

## 段階導入

1. **shadow / advisor** — 通常運用（実走・accept）に判定器を並走させ、判定と根拠を参考表示するだけ。人間の accept 判断がこの時点から安く・速くなるため、較正が完了する前から投資が回収され始める。並走の予測と実際の結果の対照が較正データにもなる（変更頻度 4.5 件/日の実測から、2 週間で 60 件超が集まる見込み）。
2. **mutation 較正** — 上記コーパスで偽陰性率・偽陽性率を測定し、グレー帯の裁定を基準文へ反映する。
3. **自動記録の解禁** — 解禁ライン到達後、`unaffected` 判定の `accepted-semantic` 自動記録を有効化する。人間は集計の独立カウントと抜き打ち監査で健全性を見張る。

## 間接依存の扱い（宣言の「踏む」の定義）

シナリオが「自分はどのファイルを使うか」を申告する宣言（`exercises`）について、参照の連鎖をどこまで「踏んだ」とみなすかという未決事項があった（レビュー指摘 cc-1: 契約 A を宣言したシナリオは、A の本文が判断基準を委ねている契約 B も間接的に踏んでいるのではないか）。本仕様は次のように定める。

- **宣言の「踏む」は、シナリオの実行が直接読むファイルに限る。** 参照 1 段先まで宣言義務を広げる案は採らない — 実測で確認したところ、人気契約のリンク先が変わるたびに再走対象が 4 本から 18 本へ跳ね上がり、部分再走で得た経済性を返上してしまうため。また、リンクの機械展開は「判断を委ねる送り」と「ただの関連参照」を区別できず、過大請求が構造的に避けられない。
- **間接依存の安全網は、本仕様の判定器が担う。** 契約 B の変更を判定器が精査するとき、B の内容がどのシナリオの要件充足に効くかは意味の問題であり、まさに判定器が見る対象である。宣言の網（構文的・可能性ゼロの申告）から漏れる間接影響を、判定の網（意味的・確率的な精査）が受け止める、という二層構成になる。
- リンク 1 段先の変更を「間接依存の可能性あり」として**警告表示する**案（診断であって強制ではない）は、判定器の導入後にその必要性を再評価する。判定器の `unclear` / `affected` 表示が同じ役割をより高い解像度で果たす見込みが立ったためで、先に作り込まない。

## この仕様が変えないもの

- 台帳のゲートの意味論（stale は記録された判断でのみ解消される）
- `pass` の意味（実走で確かめた、以外の何ものでもない）
- severity の 3 分類と、`prose-change` / `contract-addition` の既存の安価な経路
- 宣言（exercises）の意味論（可能性ゼロの人間宣言であり、台帳判定に使える）
- 人間が最終判断を持つこと（判定器はどの段階でも推奨と記録を超えない）
