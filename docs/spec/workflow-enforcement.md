# ワークフロー強制ゲート（幹の手順を、破れない形で配る仕組み）

## 前提となる言葉

- **スキル** — このリポジトリが配っている「エージェント（AI に作業させる仕組み）への手順書」。
- **幹（trunk）** — このリポジトリが定める、なにかを作るときの正式な流れ。「発話または Issue →
  brainstorm（壁打ち）→ plan（実装計画）→ 実装 → レビュー → 文書への書き戻し → PR（プルリクエスト、
  変更の取り込み依頼）」。
- **consumer プロジェクト** — このスキル集を plugin（配布用の拡張パッケージ）として導入して使う側の
  プロジェクト。このリポジトリ自身ではない。
- **ハーネス** — エージェントを動かしている実行環境そのもの。環境によっては、エージェントがコマンドを
  実行する直前に割り込んで可否を判断する仕組み（本文書では「ツール実行前フック」と呼ぶ）を持つ。
- **evidence（検証証跡）** — レビューや文書整合チェック（doc-check）を実際に実行した事実を、対象の
  コミット（git が変更につける識別子 = SHA）へ紐づけて残す記録。形式は既存の品質ゲート契約
  （skills/shared/references/ の quality-gate-contract.md と evidence-format.md）が定めている。
- **session-start 注入** — plugin がセッション開始時に、幹の案内文をエージェントの文脈へ自動で
  読み込ませる既存の仕組み。

## 解決する問題

実際の consumer プロジェクトで、幹の手順が丸ごと無視されるセッションが観測された。実装スキルも
コミットスキルも発火せず、テストファースト開発は行われず、レビューと文書整合チェックを経ないまま
push されかけ、仕様書は生成されず、main（既定ブランチ）へ直接コミットされた。

このとき session-start 注入で幹の案内は文脈に入っていた。つまり「知識として入れる」だけでは、実装に
没頭したエージェントには届かない（この想起の失敗は過去の計測でも確認済み）。一方で、対策には次の
制約がある。

1. スキルの手順書に何を書き足しても、**スキルが発火しないセッションには届かない**。
2. consumer プロジェクトの状態（git hooks、設定、git 管理対象のファイル）に**勝手に書き込んではならない**。
3. 毎プロンプトの注入は文脈を汚染するため**採らない**。

## 方針 — ハーネス側ゲート

plugin がツール実行前フックを配布し、エージェントの git 操作の直前に割り込む。フックはハーネス側に
住むため、consumer リポジトリには何も書き込まれず、人間が自分の手で行う git 操作には一切影響しない。
縛られるのはエージェントだけである。

ゲートの応答は 3 段階。

| エージェントの行動 | ゲートの応答 |
|---|---|
| 規律に適合（作業ブランチ上、evidence あり） | 素通し。メッセージも出さない（文脈汚染ゼロ） |
| 違反（main で commit、evidence なしで push） | 人間へ確認を出す。人間の承認が正規の「恩赦」 |
| バイパス工作（`--no-verify` などの検査回避フラグ） | 問答無用で拒否 |

原則: **エージェントは恩赦を申請できるが、発行できない**。違反時の確認メッセージは、破られた規律を
その瞬間に思い出させるリマインダも兼ねる。

## 守る遷移点

1. **main 直コミット** — 既定ブランチ上での commit は人間確認へ。
2. **evidence なし push** — HEAD（いま push しようとしているコミット）に紐づくレビュー evidence が
   無ければ人間確認へ。
3. **doc-check 未実施** — 2 と同じ push 検査に統合し、doc-check の evidence も要求する。

初版では、幹の採用を宣言したプロジェクトの全 push で 2・3 の両方を要求する。文書に無関係な変更での
誤検知は人間の恩赦で受け、恩赦の記録が溜まってから要求範囲を実データで絞る。

## 幹採用の宣言

evidence の要求は「幹で回している」ことを前提とするため、plugin を導入しただけのプロジェクトへ
押し付けてはならない。採否は人間の意思決定であり、設定ファイルへの明示宣言で表す。宣言が無い状態で
該当操作が起きたら、機械は勝手に判断せず**初回にユーザーへ確認し、回答を設定ファイルへ書き込む**。
main 直コミットを常用するプロジェクトの許可設定も、同じ「聞いて永続化する」型で扱う。
（宣言ファイルの置き場は実装計画側で確定する。第一候補はエージェント設定ツリー `.agents/config/`。）

## 恩赦の記録と証跡の強度

- evidence は SHA への紐づけとスクリプト経由の生成でハードルを上げる。
- 人間確認の際は「この evidence は何を根拠にしているか」を提示する。
- 恩赦（承認によるゲート通過）は記録し、形骸化（承認の常態化）を後から検査できるようにする。
- **完全な偽造防止は非目標**。エージェントがファイルを書ける以上、原理的に不可能であり、
  「ハードルを上げ、違反は必ず人間の目に触れさせる」線で費用対効果を取る。

## プラットフォーム差

ツール実行前フックの有無と表現力は環境ごとに異なる。対応環境では plugin が自動配線し、非対応環境では
散文フォールバック（注入文書での規律提示）と手動配線手順の文書化で補う。環境別の強制力の序列は
README に明記する。実装前に、各環境の実現手段の棚卸し調査を行う。

## 散文側の補修（ゲートの補助線）

- **plan 作成の受け側検査** — 参照する壁打ちの出口契約が CONVERGED（収束済み）なのに仕様書のパスが
  無い場合、plan 作成は停止して指摘する。生成側の自己申告より受け側の検査のほうが強い。
- **routing 行の追加** — session-start 注入される幹の案内（using-workflow）に「『実装して』
  （合意済みの plan がある）→ cycle（計画を自動実装するスキル）」の行を足す。実測された発火漏れの補填。

## やらないこと（非目標）

- consumer リポジトリへの git hook 設置
- 毎プロンプトの注入
- 完全な evidence 偽造防止
- 人間自身の git 操作への介入
