# evidence 記帳層の解体（検証は存続、記帳を畳む）

## 前提となる言葉

- **evidence（証跡）** — このリポジトリが「リリースや main 前進のような保護対象の状態遷移は、対象の正確な版（SHA）に結びついた検証の記録なしには成立しない」という契約（quality gate 契約）のもとで作ってきた、検証実施の記録。JSON ファイル（machine_verified.json / semantic_reviewed.json）として `.agents/artifacts/reviews/evidence/` に書かれ、リリース時に機械検査されていた。
- **記帳層** — 証跡を SHA に結びつけてファイルに記録し、公開時に検査する建て付けの総称。証跡スキーマ・検査スクリプト・リリース時の生成/検査ステップ・セッション開始時の注入が該当する。
- **検証本体** — 検証の実施そのもの。テストと整合検査（run_checks）・レビューの実行・リリース前検査。これは存続する。
- **durable marker** — 処理が中断したことを後から検出するための記録。main 前進の安全策が「未完了の公開処理がある」ことを知るために使う。

## 解決する問題

証跡を SHA に結びつけて記帳し、公開時に機械検査する仕組みは、設計としてはオーバーエンジニアリングであり、運用上は形骸化していた。

- 証跡を機械的に消費しているのはリポジトリ全体でリリースワークフローの 1 箇所だけであり、しかも同じワークフロー内で証跡を生成した直後に自分で検査する自己充足構造で、検査として機能していない。
- PR マージ時に証跡を機械検査する仕組みは存在せず、契約の要求はセッション開始時の注入による想起頼みだった。
- 証跡はローカル生成の自己申告であり、PR 上で真正性を保証できない。
- 一方で「evidence」の語は 78 ファイルに浸透し、毎セッションの注入コストを含めてトークンコストが常態化していた。

## 方針

検証の実施と検証の記帳は別物である。畳むのは検証ではなく検証の記帳であり、検証そのものは「省略する選択肢を出さない」という従来の裁定を維持する。記帳と検証の定義が一体化した契約文書は、記帳の記述を外した形に書き直して残す。

## 解体するもの（削除）

- 証跡ファイル（machine_verified.json / semantic_reviewed.json）を生成・検査する機構一式
  - 検査スクリプト `skills/shared/scripts/evidence_check.py`
  - リリースツールの証跡生成サブコマンド
  - リリースワークフローの証跡生成ステップと検査ステップ
  - セッション開始時に契約を注入するフックと、OpenCode プラグインの品質ゲート案内
  - 証跡スキーマ文書（evidence-format.md）
- 適合プロファイル文書（skill-repository-profile.md）。役に立つ中身（変更の種類からレビュー義務を導く表）は下記の契約書き直しに吸収する。

## 検証の定義（書き直して残す）

quality gate 契約文書は、証跡の記述（状態機械・証跡の束縛と失効・プロファイル層・アダプターの章）を外し、次の検証の定義だけを残した形に書き直す。

- レビュー義務（常時適用の不変条件・変更の種類から発火する義務表）
- 収束条件（レビューが何を満たせば合格とみなせるか）
- レビュー出力の台帳（coverage の状態・判定の語彙・独立性の定義）

## semantic_reviewed の機械化

リリース時の「意味レベルのレビューを経た」という人間の宣誓（チェックボックス入力）は廃止し、品質ゲート通過の保証を機械検証に置き換える。

- リリース時に、未リリース節の各エントリが参照する PR が、必要な検査を通ってマージ済みであることを `gh` で確認する。
- 品質ゲートを通す必要がない小さな変更（エントリ単位）は、理由を添えた明示の免除表記（`none — 理由`）で可視化する。黙ってスキップされる状態を作らない。
- リリース実行の承認（リリースしてよいか）は人間の判断として残す。これは品質ゲートではなくリリースの承認である。

## publication の安全策（evidence から分離して存続）

main 前進の安全策は残す。ただし、安全策が使っていた「検証済み証跡」の部分だけを外し、破壊的操作の安全を担保する構造的検査に置き換える。

- 未完了の公開処理を検出する durable marker（staging ディレクトリ）は残し、中身は検証済み証跡ではなく「この merge は意図された」ことの記録とする。
- 安全策のうち機械検証可能な構造チェック（compare-and-swap・ロック保持・merge の形・作業ツリーの安全）はすべて残す。
- 検証済み証跡の内容検査だけを外す。品質は呼び出し元のレビューが担う。

## やらないこと

- 検証の実施を省略する選択肢は設けない（従来裁定の維持）。
- 過去のリリースに記録された証跡（履歴）は書き換えない。
- 検証一般の規律（完了を証拠なく宣言しない）は変更しない。
