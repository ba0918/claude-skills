# brainstorm（要件と仕様を詰め切る、幹の入口フェーズ）

## 前提となる言葉

この文書を読むのに必要な言葉を先に説明する。

- **スキル** — このリポジトリが配っている「エージェント（AI に作業させる仕組み）への手順書」。
- **幹（trunk）** — このリポジトリが定める、なにかを作るときの正式な流れ。「発話または Issue → brainstorm → plan（実装計画）→ 実装 → レビュー → 文書への書き戻し → PR」。幹の図の正本はスキル著述規範（skill-authoring）にある。
- **exit contract（出口契約）** — brainstorm のセッションが終わるときに残す構造化された成果。「合意したこと」「まだ決めていないこと」「何ができたら完成か（受入基準）」の 3 点セット。
- **選択肢 UI** — エージェントが「A / B / C から選んでください（A 推奨）」の形で答えを迫る画面部品。

## 解決する問題

要件や仕様を詰めないまま実装が始まると、その歪みは後工程で必ず高くつく。実装計画が「なんとなくの理解」で書かれ、文書は実装とズレ、Issue は「何が書いてあるかわからないけど、やってもらうか」という儀式になる。人間が監督しているつもりで、実質は何も判断していない状態が生まれる。

brainstorm はこの問題への入口側の答えである。**アイデア出し → 要件定義 → 仕様定義を、壁打ち（対話）で徹底的に詰め切る場**であり、雑談やアイデアメモ取りの道具ではない。ここで詰め切られた合意だけが、実装計画（plan）へ進む資格を持つ。

## 幹での位置と入口

- brainstorm は幹の**既定の入口**である。なにかを作る・変える話は、まず brainstorm を検討する（漏斗の原則）。例外となる作業カテゴリ（コミット、引き継ぎ等の終端作業）はスキル著述規範の例外リストに列挙される。
- **Issue 起点でも経路を分岐させず、必ず brainstorm を経由する**。Issue の内容が既に整理されているなら、「要はこういうことだよね？」の確認が短く終わり、そのまま次へ進むだけである。十分かどうかを機械で判定する仕組みは作らない — 判定と整理は同じ壁打ちの中で自然に済む。
- 実装計画（plan）側には元ネタの確認（brainstorm の合意 / 仕様書 / バグの再現手順のどれかがあるか）が置かれ、どれも無い場合は brainstorm を経ていないことを確認してから進む。

## 対話の規律

- **セッション中の対話は自然言語のみで行う。選択肢 UI の提示は絶対に行わない。**「(推奨)」付きの選択肢を出すと、ユーザは考えずにそれを選ぶ — 要件定義の場で最も避けるべき儀式化を、道具の形が再生産してしまう。問いは常に開いた形（なぜ？ 何があれば十分？ それが無いと何が困る？）で投げ、ユーザ自身のことばで答えてもらう。
- セッション中はファイルを編集しない（読み取り専用の調査は可）。実装の提案や着手はしない。
- 議論が特定の技術に引き寄せられたときは、「その技術を使わないとしたら何を解決しようとしているのか」を問い直す。

## 出口の契約

セッションの成果は wrap（まとめ）で exit contract に構造化される。

- **合意（Agreements）**: 決めたことと、その理由。
- **未決事項（Undecided Items)**: 開いたままの問いと、それが実装計画を塞ぐか否か。塞ぐ未決が残る場合、出口は BLOCKED となり、plan には進めない。
- **受入基準（Acceptance Criteria）**: 何ができたら完成かの観察可能な条件と、機械検証の可否。
- 全ての塞ぐ未決が解消されている場合のみ CONVERGED となり、次の行き先（routing）へ流せる。

### routing（合意の行き先）

CONVERGED の合意は次のいずれかへ流す。

| 行き先 | 何が行くか |
|---|---|
| plan | 合意と受入基準を種にした実装計画の作成 |
| GitHub issue | 合意を段階単位で起票する。**brainstorm 産の issue は本文が壁打ち済みの要件そのもの**になり、人間が読んで監督できる（起票時点でヒューマンリーダブルであることが起票側の契約） |
| docs/spec | 仕様書の生成・更新（人間の承認後に書く） |
| ledger / spec-verify（支線） | 幹には配線しない。意思決定の記録を残したいとき（ledger）、仕様からテストを自動化したいとき（spec-verify）にだけ乗り換える |

## この仕様が変わるとき

この文書は brainstorm の**振る舞いの正本**であり、スキル本文（SKILL.md と分割された workflow ファイル）はこの仕様への追随として書かれる。仕様と本文が食い違ったときは、この文書を先に直してから本文を追随させる。
