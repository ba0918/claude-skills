# Design System Contract

The contract shared by the design-system skills (design-scaffold, design-generate,
design-validate, design-lint, mockup-diff).

## Core Principle: Human-in-the-Loop Once

Human subjective judgement is concentrated into **a single approval of the base design**. After
approval, quality is assured entirely by mechanical verification.

## File Structure Contract

The file structure of the target project the design-system skills operate on:

```
target-project/
├── DESIGN.md                          # human-readable design system definition
├── .design/                           # machine-readable design system
│   ├── tokens.json                    # design tokens (colors, fonts, spacing)
│   ├── tokens.css                     # CSS custom properties (generated from tokens.json)
│   ├── component-catalog.json         # component specification definitions
│   ├── layout-rules.json              # layout constraints
│   ├── pages/                         # page composition definitions
│   │   └── {page-name}.json
│   ├── rubric.json                    # evaluation criteria
│   ├── lint-config.json               # lint configuration
│   ├── baseline/                      # approved baseline
│   │   ├── approval.json              # approval metadata
│   │   └── screenshots/              # screenshots at approval time
│   └── mockup-diff/                   # artifacts generated by the mockup-diff skill
│       ├── config.json                # project-specific comparison settings
│       ├── compare.mjs                # auto-generated comparison script
│       ├── mock-responses.json        # API mock responses (when applicable)
│       └── screenshots/              # screenshot output
├── components/{framework}/            # generated components
└── mockups/base/                      # base mockups for approval
```

## Token Reference Contract

### References inside tokens.json

When a component or layout-rules references a token value, use the `$tokens.{path}` form:

```
$tokens.colors.primary      → the value of colors.primary in tokens.json
$tokens.depth.raised         → the value of depth.raised in tokens.json
$tokens.spacing.scale[2]     → the value of spacing.scale[2] in tokens.json
```

### CSS Custom Property Naming Convention

The rule for converting a tokens.json key path into a CSS custom property name:

| tokens.json path | CSS custom property |
|-----------------|---------------------|
| `colors.primary` | `--color-primary` |
| `colors.primaryHover` | `--color-primary-hover` |
| `colors.textPrimary` | `--color-text-primary` |
| `typography.headingFont` | `--font-heading` |
| `typography.bodyFont` | `--font-body` |
| `typography.scale.h1.size` | `--font-size-h1` |
| `typography.scale.h1.weight` | `--font-weight-h1` |
| `typography.scale.h1.lineHeight` | `--line-height-h1` |
| `spacing.baseUnit` | `--spacing-base` |
| `spacing.scale[N]` | `--spacing-{N}` (0-indexed) |
| `components.buttons.borderRadius` | `--radius-button` |
| `components.cards.borderRadius` | `--radius-card` |
| `components.inputs.borderRadius` | `--radius-input` |
| `depth.raised.shadow` | `--shadow-raised` |
| `depth.overlay.shadow` | `--shadow-overlay` |
| `depth.modal.shadow` | `--shadow-modal` |
| `depth.toast.shadow` | `--shadow-toast` |

**camelCase → kebab-case conversion rule:** insert a hyphen before each uppercase letter and
lowercase it. Examples: `primaryHover` → `primary-hover`, `textPrimary` → `text-primary`

## Verification Hierarchy Contract

Verification runs in the following order. When an upper level fails, the lower levels do not
run:

```
Level 1: Static Lint (AST analysis)
  ├── DL001-006: detect hard-coded tokens
  ├── DL101-103: detect component violations
  └── DL201-204: detect page composition violations

Level 2: Schema Validation
  └── tokens.json / catalog.json / pages/*.json conform to their schemas

Level 3: Visual Regression Test
  └── diff against the approved baseline screenshots

Level 4: Rubric Judge (LLM)
  └── evaluation of "cohesion" and "naturalness of the experience", which cannot be verified mechanically
```

**Weight distribution:** mechanical (60%) > visual (22%) > llm-judge (18%)

## Lint Rule ID Scheme

| Range | Category | Description |
|------|---------|------|
| DL001-099 | Token Compliance | Detect hard-coded tokens |
| DL100-199 | Component Compliance | Detect component violations |
| DL200-299 | Page/Layout Compliance | Detect page composition violations |
| DL300-399 | (future expansion) | |

## Baseline Re-approval Triggers

Re-approval of the baseline is required under the following conditions:

1. The hash of `tokens.json` disagrees with `tokensHash` in `approval.json`
2. The hash of `component-catalog.json` disagrees with `catalogHash` in `approval.json`
3. `approval.json` does not exist

Updating the baseline without re-approval is **prohibited**.

## Framework Adapter Contract

Each framework adapter provides the following:

| Artifact | React/Preact | Flutter | VanillaJS | PostCSS |
|--------|-------------|---------|-----------|---------|
| Theme object | `theme.ts` | `theme.dart` | — | — |
| CSS variables | `tokens.css` | — | `tokens.css` | `tokens.css` |
| Components | `{Name}.tsx` | `{name}.dart` | `{name}.js` | — |
| Storybook | `.stories.tsx` | — | `.stories.js` | — |

**Common:** tokens.css (CSS custom properties) is shared by every web framework.

## The Place of mockup-diff

### Position in the pipeline

```
design-guide → design-scaffold → design-generate
         ↓                              ↓
    [HUMAN APPROVAL]               mockups/base/*.html
         ↓                              ↓
    baseline fixed                 implemented in the app
         ↓                              ↓
    design-validate                mockup-diff
    (mechanical verification       (verification of implementation
     of token compliance)           quality: mock vs real app)
```

### Division of labor with design-validate

| | design-validate | mockup-diff |
|--|----------------|-------------|
| **What is compared** | baseline screenshots vs implementation code | mockup HTML vs the running app |
| **What it detects** | hard-coded tokens, undefined tokens, pixel diffs | spacing drift, broken fonts, layout bugs in dynamic states |
| **Verification level** | compliance with mechanical rules (automatic judgement) | the last mile of implementation quality (LLM visual inspection + manual fixes) |
| **When it runs** | CI / on code changes | after the design has been brought into the app |

### Files specific to mockup-diff

In Phase 0: SETUP, mockup-diff investigates the project and generates a tailor-made comparison
script under `.design/mockup-diff/`. The generated files:

- `config.json`: framework kind, dev server settings, navigation method, API mocking approach, etc.
- `compare.mjs`: a Playwright-based screenshot capture and comparison script
- `mock-responses.json`: API mock responses (when `apiMock.type` is anything other than `none`)
- `screenshots/`: the screenshot output directory
